# Plan: ManaBox decklist (.txt) import with partner commanders
Date: 2026-09-19
Status: COMPLETED

## Problem

Users can already import their card *collection* from a ManaBox CSV export (`plans/2026-08-31-collection-import-slice.md`) and build decks via LLM suggestion (`plans/2026-09-07-llm-deck-features-slice.md`), but there's no way to bring in a deck they already built in ManaBox itself. ManaBox only exports built decks as a `.txt` decklist, not CSV, and that decklist can name two commanders (a Partner/Background pair) - a case this app's UI and color-identity logic don't handle today (`Deck.commanderCardId` is treated everywhere as a single card). This slice adds a decklist importer that creates a new deck from a ManaBox `.txt` export, including decks with two commanders, and lets the user switch which of the two is the deck's active commander.

## Scope

**In scope:**
- A parser for the ManaBox `.txt` decklist format: a `// COMMANDER` section (one or two card lines) followed by a blank line and an unlabeled mainboard section; each line is `<quantity> <name> (<setCode>) <collectorNumber>` with an optional trailing `*F*` foil marker. Set code, collector number, and foil marker are discarded for matching (this schema's `Card.name` is unique - no per-printing rows); duplicate name lines (e.g. a foil and non-foil printing of the same card) are summed into one quantity.
- `POST /api/decks/import` - creates a new `Deck` from an uploaded `.txt` file: matches every line's card name against the local catalog case-insensitively, creates `DeckCard` rows for every match (both commander lines get `isCommander: true`, quantity forced to 1; mainboard lines get `isCommander: false` with their summed quantity), and reports any line whose name didn't match any catalog card as `unmatchedNames` in the response. Ownership is **not** checked at import time - cards the caller doesn't own are imported anyway (see next point).
- A live-computed "not owned" indicator on the deck detail page: any `DeckCard` whose card isn't in the caller's `CollectionEntry` set is flagged in the UI. Not persisted - computed by cross-referencing the caller's collection on read, since a stored flag would go stale the moment they buy the card.
- Two-commander ("partner") support: `Deck.commanderCardId` keeps its existing meaning (the single *active* commander used everywhere color-identity is checked and displayed as "the" commander), while `DeckCard.isCommander` may now be `true` on up to two rows for the same deck (both partner candidates). `POST /api/decks/[id]/commander` lets the caller swap which of the two becomes `commanderCardId`.
- Everywhere color identity is checked or displayed against "the commander" today, switch to the *union* of every `isCommander: true` `DeckCard`'s `colorIdentity` for that deck, so a partner deck isn't incorrectly narrowed to only one commander's colors. This touches `src/lib/deck-builder.ts`, `src/lib/card-suggestion.ts`, `src/app/api/decks/[id]/cards/route.ts`, and the client-side filter in `src/app/decks/[id]/page.tsx`.
- New UI: a `/decks/import` upload page (linked from `/decks` as "Import decklist", alongside the existing "New deck" button), and deck-detail-page changes: render every commander row (not just one) with a "Make active" control on whichever one isn't currently `commanderCardId`, and a "Not owned" badge per the ownership indicator above.

**Out of scope:**
- Validating that a two-commander pair is an actually-legal Partner/Background combination (oracle-text/keyword checking) - the second commander line only needs to resolve to a real catalog card; legality of pairing them is trusted from the import, same as the rest of this app trusts an LLM-built or manually-edited deck until `critique` is requested.
- More than two commander lines in the `// COMMANDER` section - rejected with a 400, not truncated or merged.
- Enforcing singleton, color identity, or the 100-card total on the imported decklist itself - it's accepted as-is (matching the manual-deck-editing slice's precedent that a deck is allowed to sit away from full legality mid-edit; `critique` already independently gates on exactly 100 cards).
- A resolution queue for catalog-unmatched decklist lines (unlike collection import's `UnmatchedImportRow` flow) - unmatched names are reported once in the import response and not persisted; the user can re-import after fixing the line, or add the card manually via "Add from collection" afterward.
- Decklist *export* (Manabox format or otherwise) - only import.
- Any format other than this exact ManaBox `.txt` shape - no `// SIDEBOARD` handling, no generic "1x Card Name" Arena-style parsing.

## Success criteria

1. `npm test` passes with no failing tests, and `npm run build` succeeds.
2. Importing a `.txt` file with a single commander line creates a deck identical in shape to one created via `/decks/new` (one `isCommander: true` `DeckCard`, `Deck.commanderCardId` set to it).
3. Importing a `.txt` file with two commander lines creates a deck with two `isCommander: true` `DeckCard` rows and `Deck.commanderCardId` set to the first; `POST /api/decks/[id]/commander` with the second card's id flips `commanderCardId` to it; passing a `cardId` that isn't one of the deck's commander rows returns 400.
4. A decklist line naming a card the caller doesn't own still produces a `DeckCard` row for it; a line whose name matches no catalog card at all is skipped and listed in the response's `unmatchedNames`.
5. On the deck detail page, a card not in the caller's collection shows a "Not owned" badge; adding it to their collection (or importing a deck after they already own it) removes the badge on next load.
6. Adding a card via `POST /api/decks/[id]/cards`, requesting suggestions, or building a deck for a two-commander deck all accept/offer cards within *either* commander's color identity, not just the active one's.
7. `POST /api/decks/import` returns 401 with no session, 400 for a non-`.txt`/unparseable file, 400 if the `// COMMANDER` section is missing or has more than two lines or its first line doesn't resolve to a commander-eligible card.

## Self-review

- No Prisma migration is required: `DeckCard.isCommander` is a plain boolean with no constraint limiting it to one `true` row per deck, and `Deck.commanderCardId` keeps its existing single-FK meaning as "the active commander" - confirmed by reading `prisma/schema.prisma` rather than assumed, per the Context-to-load note.
- The "not owned" indicator is deliberately computed live (cross-referencing `CollectionEntry` on read) rather than stored on `DeckCard`, so it can't go stale if the user's collection changes after import - this was a real design fork (store vs. compute) and computing was chosen explicitly rather than left implicit.
- Group B's four call-site updates (build, suggest-cards, add-card, and the client page) were found by grepping every reference to `commanderCard.colorIdentity` / `commander.colorIdentity`, not guessed - Task descriptions name the exact current include/line to change in each file so a sub-agent doesn't have to re-derive them.
- Group E explicitly depends on B (needs `unionColorIdentity` to exist), C (needs the switch-commander endpoint), and D (needs the import endpoint) - it's the only sequential group; A, B, C, D all touch disjoint files and can run in parallel.
- Partner/Background legality (whether the two named commanders are *actually* allowed to pair) is explicitly out of scope and called out twice (Scope and Task 7) so it isn't silently half-implemented - the import trusts the `.txt` file's two commander lines the same way the rest of this app trusts an already-built or manually-edited deck.
- Every new route follows the exact 401/404/403/400 convention and response shape (`commanderCard` + `cards.card` included) already established by `src/app/api/decks/[id]/cards/[cardId]/route.ts`, so no new error-handling pattern is introduced.
